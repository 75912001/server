# 服务级别版本更新设计

本文记录 server 项目中“服务级别版本更新”的设计讨论。当前阶段只讨论设计, 不改代码。

## 已确认上下文

- 服务范围包含 login、gateway、online、cache。
- 各服务配置中已有 `base.version`, 该字段当前主要作为服务版本信息写入配置和服务发现元数据。
- login 通过 etcd 发现 gateway/cache, gateway 通过 etcd 发现 online/cache/gateway peer, online 通过 etcd 发现 cache。
- login 选择 gateway、gateway 选择 online 时当前主要依赖可用性和 `availableLoad`。
- 扩容设计已约束: 新实例只接新流量, 不迁移已有 TCP 连接或 online actor。
- gateway 持有客户端 TCP 连接和本地 `Account` actor。
- online 持有账号业务 actor。
- cache 是无状态 Redis 访问层, 底层 Redis Cluster 是共享数据源。
- `connectTicket` 有独立的 payload 协议版本, 这和服务 `base.version` 不是同一个概念。

## 术语边界

### 服务版本

服务版本指 login、gateway、online、cache 某个服务实例运行的二进制、配置和内部行为版本。它用于描述实例自身是否属于某次发布。

### 协议版本

协议版本指跨进程或客户端可见的数据契约版本, 例如 proto 字段语义、Redis key/hash 结构、Lua CAS 语义、`connectTicket` payload 版本。

服务版本可以频繁变化, 协议版本应更谨慎变化。一次服务版本更新不一定包含协议版本变化。

## 已确认决策

### 1. 普通服务级别更新要求新旧版本短时间共存

服务级别滚动更新的核心问题是: 同一服务或不同服务之间, 是否允许短时间内新旧版本同时运行并互相调用。

- 默认要求新旧服务版本可短时间共存。
- 普通服务级别更新必须保持跨服务 RPC、TCP 客户端协议、Redis 数据结构和 `connectTicket` 语义兼容。
- 不兼容协议变化不归类为普通服务级别更新, 需要单独设计灰度、双写双读、expand-contract 或停服维护方案。

### 2. 默认先扩新版本再摘旧版本

服务级别版本更新需要确认发布形态: 是直接停止旧实例并用新版本原地启动, 还是先启动新版本实例进入服务发现, 再把旧版本实例摘流并排空。

- 默认采用先扩新版本再摘旧版本。
- login/cache 可以滚动替换, 但仍建议先确认新实例健康后再移除旧实例。
- gateway/online 必须按有状态服务处理: 新版本只接新登录和新绑定, 旧版本停止接新流量后等待已有 TCP 连接和 online actor 自然下线。
- 原地重启只用于开发环境、无在线账号实例, 或明确允许断线的维护窗口。

### 3. 普通服务级别更新不做强制版本隔离

先扩新版本再摘旧版本意味着一段时间内会同时存在新旧服务实例。需要确认 login 选择 gateway、gateway 选择 online、服务间 gRPC 调用是否需要按 `base.version` 做硬隔离或亲和。

- 普通服务级别更新不做强制版本隔离。
- `base.version` 用于观测、日志、发布验收和人工排障, 不作为默认路由条件。
- 新旧版本必须能互相调用; login 可以选择旧 gateway 或新 gateway, gateway 可以选择旧 online 或新 online。
- 如果某次发布要求 gateway 和 online 必须同版本配对, 则这不是普通服务级别更新, 需要单独设计版本围栏、灰度入口或停服维护。

### 4. 多服务同时更新时默认按依赖从底向上

一次发布可能同时包含 cache、online、gateway、login 的代码或配置变化。需要确认默认更新顺序, 以及是否允许多服务并行更新。

- 默认顺序按依赖从底向上: cache -> online -> gateway -> login。
- cache 先更新, 因为它承载 Redis 数据访问和 CAS 语义, 上层服务依赖它的兼容性。
- online 再更新, 因为 gateway 新登录绑定会调用 online。
- gateway 再更新, 因为 login 签发的 `connectTicket` 会绑定目标 gateway。
- login 最后更新, 因为它是新登录入口, 最容易通过外部 LB 灰度和回滚。
- 只有确认发布内容互不依赖且兼容性测试覆盖充分时, 才允许并行更新多个服务。

### 5. 新版本实例通过门禁后才能摘旧版本

先扩新版本再摘旧版本时, 新实例启动成功并写入 etcd 只是“可被发现”。需要确认旧版本是否可以立即摘除, 还是必须先通过健康检查和小流量验证。

- 每个服务先扩 1 个新版本实例作为金丝雀实例。
- 新实例必须通过启动日志、etcd key、gRPC/HTTP/TCP 监听和关键链路验证后, 才开始摘除同服务旧实例。
- login 验证 HTTP 登录接口和 gateway 选择结果。
- gateway 验证 TCP 登录、`connectTicket` 校验、cache accountSession CAS 和 online bind。
- online 验证 `OnlineBindAccount`、Account actor 创建和 cache AccountRecord 读写。
- cache 验证 Redis 连接、accountVerifyToken、AccountRecord 和 accountSession CAS。
- 任一门禁失败时停止摘旧版本, 保留旧版本继续承载流量, 新版本按故障实例处理。

### 6. 回滚默认只影响新流量

普通服务级别更新允许新旧版本共存, 因此回滚可以理解为“停止继续放量新版本, 恢复旧版本承载新流量”。需要确认已经进入新版本 gateway/online 的在线账号是否迁移或强制踢下线。

- 回滚默认只影响新流量, 不迁移已有 TCP 连接或 online actor。
- 发现问题后先摘除新版本实例: login 不再选择新 gateway, gateway 不再选择新 online, 外部 LB 不再分流到新 login。
- 如果旧版本容量不足, 先扩旧版本实例再摘新版本。
- 已经连接到新 gateway 或绑定到新 online 的账号继续留在原实例, 除非问题影响数据正确性或玩家安全。
- 若问题影响数据正确性, 才执行明确的强制下线或停服恢复流程。
- cache 回滚必须额外确认 Redis 数据结构兼容; 如果新版本已经写入旧版本不能理解的数据, 不允许普通回滚, 必须走数据修复或兼容补丁。

### 7. 普通服务级别更新不允许不兼容协议或数据结构变更

服务版本更新和协议版本更新已经区分, 但需要明确普通服务级别更新的准入边界。这里的协议或数据结构包括 proto 字段语义、TCP 包语义、Redis key/hash 结构、Lua CAS 行为、`connectTicket` payload。

- 普通服务级别更新不允许不兼容协议或数据结构变更。
- 允许向后兼容新增字段, 旧版本忽略新字段, 新版本能处理旧字段缺失。
- Redis/hash 结构只允许兼容新增字段, 旧字段语义不能原地改变。
- CAS/Lua 行为必须保持旧版本和新版本同时操作时结果正确。
- `connectTicket` payload 版本变化必须单独设计, 不能夹在普通服务滚动更新里。
- 需要不兼容变更时, 采用独立的协议升级方案, 例如 expand-contract、双读双写、版本化 key、停服维护或强制客户端升级。

### 8. 发布完成分为新流量切换完成和旧实例排空完成

先扩新版本再摘旧版本会让旧 gateway/online 继续承载已有连接和 actor。需要明确发布什么时候算完成, 以及旧版本实例什么时候可以真正停止。

- 发布完成分为两个阶段: 新流量切换完成, 旧实例排空完成。
- 新流量切换完成: 所有新登录、新绑定、新 cache 请求已经进入目标新版本实例, 且关键指标稳定。
- 旧实例排空完成: 旧 gateway 的 TCP 连接数为 0, 旧 online 的 user actor 数为 0, 旧 login/cache 已从外部 LB 或服务发现中摘除且无进行中请求。
- gateway/online 在排空前不能强制停止, 除非进入维护窗口或故障处置。
- 发布验收报告必须记录每个服务的新旧实例数量、版本号、etcd key、流量切换时间、排空时间和异常指标。
- 如果长期无法排空, 进入人工决策: 继续等待、通知玩家维护、或执行强制下线。

## 待确认问题

### 9. gateway/online 摘流时是否保留 etcd 身份

gateway 和 online 是有状态服务。旧实例摘流后仍可能承载已有 TCP 连接、user actor、顶号控制请求和清理请求。需要确认摘流是否直接删除 etcd key。

推荐决策:

- gateway/online 摘流时保留 etcd server key, 直到排空完成。
- 摘流状态只阻止新流量分配, 不阻止已有连接、已有 actor 和服务间控制请求。
- gateway 摘流后 login 不再选择该 gateway 签发新 `connectTicket`, 但其他 gateway 仍能通过 gateway peer 找到它处理顶号和清理。
- online 摘流后 gateway 不再选择该 online 做新 `OnlineBindAccount`, 但已有绑定仍继续使用原 online。
- 实现上需要独立于 etcd del 的 drain 状态, 例如 `availableLoad=0` 加 drain 标记; etcd del 只表示实例真正下线。
- cache/login 这类无状态或入口服务可以由 resolver/LB 直接摘出, 不要求保留身份到排空。
