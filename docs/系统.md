# 石器时代8.5运气系统

本文档冻结角色运气从持久化、登录刷新、道具和GM修改、装备配置即时派生到战斗快照的完整规则. 数值机制以8.5当前启用源码为准, 工程边界沿用当前项目的Account actor、CharacterRecord、物品配置和CombatRoom.

配套文档:

- `docs/战斗.proto`: 战斗协议结构和运气判定快照.
- `docs/战斗规则.md`: 运气在每项战斗公式中的精确用途.

本文档同时记录已落地生产能力和后续装备系统接入边界. CharacterLuckState、登录LS日刷新、失败回滚、登录响应和CombatLuckSnapshot已经进入生产协议与online代码; EquipmentRecord明确不保存运气修正.

## 1. 结论

### 1.1 三个运气值

| 名称 | 8.5字段 | 是否持久化 | 规则 |
|---|---|---|---|
| 基础运气 | `CHAR_LUCK` | 是 | 正常角色范围1-5; 0只允许出现在首次登录刷新前 |
| 装备运气修正 | 本次从已装备物品配置读取的`ITEM_MODIFYLUCK`之和 | 否 | 可为负数或远大于5; 每次属性重算或建立战斗快照时即时累计 |
| 有效运气 | `CHAR_WORKFIXLUCK` | 否 | `clamp(基础运气+装备运气修正,1,5)` |

有效运气是派生值, 不写入角色档案. 每次登录、换装、装备移除或战斗建快照时重新计算, 避免持久化数据与装备状态不一致.

### 1.2 基础运气等级

| 数值 | 8.5名称 |
|---:|---|
| 1 | 凶 |
| 2 | 一般 |
| 3 | 小吉 |
| 4 | 中吉 |
| 5 | 大吉 |

宠物的`CHAR_VARIABLEAI`与`CHAR_LUCK`复用旧结构中的同一枚举位置, 但语义是宠物AI/忠诚变量, 不是玩家角色运气. 当前项目不得给PetRecord复用CharacterLuckState.

## 2. 8.5源码依据

| 功能 | 8.5代码 | 结论 |
|---|---|---|
| 基础字段 | `gmsv/include/char_base.h`中的`CHAR_LUCK` | 玩家基础运气 |
| 刷新时间字段 | `gmsv/include/char_base.h`中的`CHAR_LASTTIMESETLUCK` | 保存上次自动刷新时间 |
| 存档键 | `gmsv/char/char_base.c`中的`luc`和`llt` | 两个字段随角色存档 |
| 新角色默认 | `gmsv/char/defaultPlayer.h`中的`luck=0`、`last=0` | 首次登录必须刷新 |
| 登录刷新 | `gmsv/char/char.c:CHAR_setLuck` | 仅登录时检查LS日并随机1-5 |
| 登录调用点 | `gmsv/char/char.c`角色登录流程 | 在线跨LS日不会自动刷新 |
| LS时间 | `gmsv/handletime.c:RealTimeToLSTime` | 1个LS日为5400秒, 1年100个LS日 |
| 工作值初始化 | `gmsv/char/char.c:CHAR_complianceParameter` | 基础运气复制到`CHAR_WORKFIXLUCK` |
| 装备累计 | `gmsv/item/item.c:ITEM_equipEffect` | 累计已装备物品运气并限制1-5 |
| 8.5装备实例随机 | `gmsv/item/item.c:ITEM_getRandomValue`、`ITEM_makeItem` | 旧服配置上下限为闭区间, 创建实例时确定实际值; 当前项目按已确认规则不持久化装备运气 |
| 换装重算 | `gmsv/char/char_item.c` | 装备、卸下和丢弃后重新合规化并发送状态 |
| 运气道具 | `gmsv/item/item_event.c:ITEM_Luck` | 消耗道具并直接把基础运气设为1-5 |
| GM命令 | `gmsv/char/chatmagic.c:CHAR_CHAT_DEBUG_luck` | 输入限制到1-5, 修改后重新合规化 |
| 运气NPC | `gmsv/npc/npc_luckyman.c` | 按基础运气选择`luck1`至`luck5`文本 |
| 战斗用途 | `gmsv/battle/battle_event.c`、`battle_magic.c`、`battle.c` | 不同公式分别读取基础或有效运气 |

8.5的`CHAR_setLuck`和`ITEM_Luck`只修改基础字段, 自身没有立即调用`CHAR_complianceParameter`. 旧服工作值可能暂时保留旧值, 直到换装、回合预处理或其他合规化入口. 当前项目不持久化工作值或装备运气, 在角色状态响应和战斗建快照时从权威基础值与当前已装备物品配置重新派生, 保留公式和最终战斗数值, 不复制旧服容易失真的缓存时序. 由于当前可穿戴运气配置的上下限均相等, 该工程取舍不改变当前数值结果.

## 3. LS时间和自动刷新

### 3.1 LS时间常量

8.5常量:

```text
LSTIME_SECONDS_PER_DAY = 5400
LSTIME_DAYS_PER_YEAR = 100
era = 912766409 + 5400 = 912771809
```

因此:

- 1个LS日等于5400个现实秒, 即90分钟.
- 1个LS年等于100个LS日, 即540000个现实秒.
- “每日刷新”不是现实自然日、服务器时区日或UTC日.

现代毫秒时间戳转换:

```text
unixSeconds = timestampMs / 1000
lsSeconds = unixSeconds - 912771809
lsYear = lsSeconds / 540000
lsDay = (lsSeconds / 5400) % 100
```

正常生产时间均晚于era. 对`last_refresh_timestamp_ms<=0`直接判定需要首次刷新, 不依赖负数除法行为.

### 3.2 刷新时机

基础运气只在角色登录成功流程中检查:

1. 新角色`base_luck=0`且`last_refresh_timestamp_ms=0`, 首次登录必定刷新.
2. 当前LS年或LS日与上次刷新不同, 刷新一次.
3. 同一LS日反复上下线不刷新.
4. 角色保持在线跨过LS日边界不刷新.
5. 跨过多个LS日后再次登录也只刷新一次, 不补抽中间日期.
6. 战斗开始、回合开始、换地图和现实午夜都不能触发自动刷新.

### 3.3 随机分布

8.5执行`r=RAND(0,99)`, 闭区间共100个结果:

| r范围 | 基础运气 | 名称 | 概率 |
|---:|---:|---|---:|
| 60-99 | 1 | 凶 | 40% |
| 30-59 | 2 | 一般 | 30% |
| 10-29 | 3 | 小吉 | 20% |
| 3-9 | 4 | 中吉 | 7% |
| 0-2 | 5 | 大吉 | 3% |

实现必须保留闭区间、阈值顺序和概率. 测试使用可注入的确定性随机源; 普通客户端协议不发送随机种子.

## 4. 当前项目的持久化模型

### 4.1 CharacterRecord

`server/proto/character.proto`已增加:

```proto
message CharacterLuckState {
  uint32 base_luck = 1; // 0仅表示首次登录尚未刷新; 正常持久化范围1-5
  int64 last_refresh_timestamp_ms = 2; // 最近一次自动LS日刷新时间, 单位毫秒
}

message CharacterRecord {
  // 现有字段保持不变.
  CharacterLuckState luck_state = 19;
}
```

使用嵌套消息而不是两个裸标量的原因:

- proto3消息具有presence, 可以区分“字段整体缺失”和“合法的首次登录待刷新状态”.
- 基础值和刷新时间属于同一业务不变量, 应一起校验、更新和回滚.
- `CharacterRecord`的19号字段当前空闲, 20号已被`asset_id_record_map`使用.

数据不变量:

| 状态 | 是否合法 |
|---|---|
| `luck_state!=nil, base_luck=0, last_refresh=0` | 合法, 仅新角色首次登录前 |
| `luck_state!=nil, base_luck=1..5, last_refresh>0` | 合法 |
| `luck_state=nil` | 当前项目不兼容旧档案时拒绝绑定 |
| `base_luck>5` | 非法 |
| `base_luck=0, last_refresh>0` | 非法 |
| `base_luck=1..5, last_refresh=0` | 非法, 避免无法判断自动刷新周期 |

### 4.2 装备配置与EquipmentRecord

`EquipmentRecord`不保存运气修正. `server/proto/equipment.proto`已保留已移除字段的编号和名称, 避免后续误用:

```proto
message EquipmentRecord {
  reserved 2;
  reserved "luck_modifier";
  uint64 uuid = 1;
  // 现有map字段保持不变.
}
```

装备系统接入后, 已装备记录只需提供装备配置ID和穿戴状态. 服务端每次属性重算、换装、装备移除或建立战斗快照时, 根据当前已装备的配置ID查询物品配置并累加运气. 装备运气合计和有效运气都不写入EquipmentRecord或CharacterRecord:

```text
equipmentLuckModifier = sum(itemConfig[equippedEquipment.configID].luckModifier)
effectiveLuck = clamp(character.luck_state.base_luck + equipmentLuckModifier, 1, 5)
```

当前服务器尚无物品配置表和角色已装备集合, 因此生产战斗中装备修正暂为0. 不为此在档案中增加冗余运气字段.

## 5. 角色生命周期

### 5.1 创建角色

`online/account.actor.client.go:onCharacterCreateReq`创建CharacterRecord时:

1. 初始化`luck_state`消息.
2. 写`base_luck=0`.
3. 写`last_refresh_timestamp_ms=0`.
4. 不在创建角色请求中抽取运气, 与8.5首次角色登录刷新保持一致.

### 5.2 角色登录

`onCharacterOnlineReq`的推荐顺序:

1. 完成角色存在、归属和未在线等本地检查.
2. 读取当前时间一次, 得到`nowMs`.
3. 用纯函数判断当前LS年/日是否不同.
4. 需要刷新时只抽取一次`RAND(0,99)`并计算新基础运气.
5. 在内存中同时更新`luck_state`和`last_login_timestamp_ms`.
6. 一次`unaryCacheSetAccountRecord`持久化整个AccountRecord.
7. 持久化成功后再清理运行态、设置`online=true`并回复客户端.
8. 持久化失败时恢复原来的运气状态和最后登录时间, 返回错误, 角色不得进入在线态.

推荐纯函数边界:

```text
lsBucket(timestampMs) -> (year, day)
shouldRefreshLuck(nowMs, luckState) -> bool
rollBaseLuck(roll0To99) -> 1..5
calculateEffectiveLuck(baseLuck, equippedModifiers) -> (modifierSum, effectiveLuck)
```

这些函数不访问cache、actor、网络或全局时间, 便于固定向量测试.

### 5.3 登录响应

`CharacterOnlineRes`已增加刷新后的运气状态:

```proto
message CharacterOnlineRes {
  uint64 character_uuid = 1;
  CharacterLuckState luck_state = 2; // 本次登录刷新后的权威基础运气和刷新时间
}
```

客户端显示基础运气名称时使用该字段. 如果还需显示装备后的有效运气, 应由角色状态或装备状态响应返回服务端派生结果, 客户端不能自行读取配置并重算.

### 5.4 在线跨LS日

不设置刷新定时器. 在线角色即使跨过多个90分钟边界, 基础运气保持不变, 直到下一次成功登录. 这是8.5明确行为, 不能改成在线定时刷新.

## 6. 基础运气的所有修改入口

| 入口 | 新值 | 是否更新自动刷新时间 | 是否立即派生有效运气 | 现代持久化要求 |
|---|---:|---|---|---|
| 登录跨LS日 | 按40/30/20/7/3分布 | 是 | 是 | 与last_login一次写回 |
| 首次登录 | 同上 | 是 | 是 | 从0变成1-5后写回 |
| 运气戒指`ITEM_Luck` | 指定1-5 | 否 | 是 | 道具消费与角色更新必须处于同一权威事务/补偿流程 |
| GM luck命令 | 输入截断到1-5 | 否 | 是 | 写审计日志并持久化角色 |

道具或GM修改不改变`last_refresh_timestamp_ms`. 因此:

- 同一LS日内重新登录时, 指定值继续保留.
- 进入新的LS日后登录时, 指定值会被正常随机刷新覆盖.
- 不允许通过修改刷新时间让道具效果永久化, 除非未来定义不同机制版本.

### 6.1 运气戒指

`D:\csa_8.0\gmsv\data\itemset6.txt`中的“运气戒指”名称容易被误解. 它们的类型是`ITEM_OTHER`, 不能装备, 使用函数为`ITEM_Luck`, 自身装备luck列为0:

| 物品ID | 名称 | 使用结果 |
|---:|---|---|
| 20801 | 运气戒指 | 基础运气设为1, 凶 |
| 20802 | 运气戒指 | 基础运气设为2, 一般 |
| 20803 | 运气戒指 | 基础运气设为3, 小吉 |
| 20804 | 运气戒指 | 基础运气设为4, 中吉 |
| 20805 | 运气戒指 | 基础运气设为5, 大吉 |

道具处理顺序必须先校验角色和物品归属、物品参数及可用场景, 再修改角色和消费物品. 一旦开始持久化副作用, 任一步失败都必须回滚或产生显式补偿, 不能只删除物品而丢失运气修改.

### 6.2 GM命令

8.5 `CHAR_CHAT_DEBUG_luck`规则:

- 小于1改为1.
- 大于5改为5.
- 可修改自己或按账号找到的在线角色.
- 修改后调用`CHAR_complianceParameter`并发送运气状态.
- 不更新`CHAR_LASTTIMESETLUCK`.

现代GM入口必须额外保存操作者、目标角色、修改前值、输入值、截断后值、时间和原因.

### 6.3 运气NPC

`NPC_LUCKYMAN`读取基础`CHAR_LUCK`, 从NPC参数`luck1`至`luck5`中随机选择一条文本. 它不读取装备后的有效运气, 不修改运气.

## 7. 装备运气修正

### 7.1 配置解析

`itemset6.txt`为luck配置提供两个整数. 8.5执行:

```text
configMin = min(configValue1, configValue2)
configMax = max(configValue1, configValue2)
```

当前全61个可穿戴运气装备的两个配置值都相等, 因此物品配置可直接暴露单一有符号`luck_modifier`, 每次重算都得到相同结果, 不需要实例持久化. 未来如果导入两个值不相等的可穿戴装备, 配置加载必须显式拒绝, 直到确定不持久化条件下的唯一取值规则; 不得在每个战斗判定点重新随机, 否则同一件装备的效果会无规则波动.

### 7.2 装备累计和耐久

- 只扫描角色装备槽, 背包中的装备不参加.
- 武器、头、身体、两个装饰槽及启用的新腰带、盾、鞋、手套槽均按实际装备参加.
- 双装饰槽的修正相加后统一截断.
- 二刀流副手沿用8.5职业缩放逻辑; 当前带运气武器的值至少为100, 缩放后仍足以把有效运气推到5.
- 有效运气最终始终限制在1-5.
- 当前`_TAKE_ITEMDAMAGE`启用分支不会按耐久比例逐步降低运气. 装备仍存在时每次读取完整配置修正; 被删除、投掷移除或离开装备槽后才停止生效.

## 8. 战斗中的运气

### 8.1 使用矩阵

| 战斗机制 | 使用基础运气 | 使用有效运气 | 说明 |
|---|---|---|---|
| 开战先制 | 否 | 是 | 玩家侧0号位队长 |
| 普通物理闪避 | 否 | 是 | 仅玩家防守者; 合击跳过闪避 |
| 物理暴击 | 否 | 是 | 仅玩家攻击者 |
| 玩家反击 | 否 | 是 | 执行反击的玩家 |
| 通用普通异常 | 否 | 是 | 攻击者; 麻痹专用分支除外 |
| 捕获 | 否 | 是 | 捕获者 |
| PVE逃跑 | 否 | 是 | 逃跑者 |
| 普通攻击魔法闪避 | 是 | 否 | 玩家目标`CHAR_LUCK*3`; 非玩家走等级公式 |
| 职业魔法闪避 | 是 | 否 | 玩家目标`CHAR_LUCK*3`; 非玩家走等级公式 |
| 10级以上玩家空手随机多段 | 是 | 否 | 装备运气不改变段数分布 |

完整公式、随机边界和严格`<`/`<=`差异见`docs/战斗规则.md`.

### 8.2 战斗快照

`docs/战斗.proto`使用:

```proto
message CombatLuckSnapshot {
  sint32 base_luck = 1;
  sint32 equipment_modifier = 2;
  sint32 effective_luck = 3;
}
```

开战时:

1. 从CharacterRecord读取基础运气.
2. 遍历当前已装备记录, 按每件装备的配置ID查询物品配置并即时累加运气修正.
3. 计算1-5有效运气.
4. 写入`CombatUnitAttribute.luck`.
5. `runtime_attribute_list`分别记录BaseLuck、EquipmentLuckModifier和EffectiveLuck.

`EquipmentRecord`和`CombatEquipmentRuntimeState`均不保存单件装备运气. 如果战斗内已装备集合改变, 服务端再次查询配置并替换运行时合计.

每次概率判定的`CombatRandomCheck`同时记录:

- `luck_usage`: BaseLuck或EffectiveLuck.
- `luck_snapshot`: 判定发生时的三个完整值.
- 参与公式的实际数值和随机闭区间.

客户端只展示服务端结果, 不能依据运气重算命中、暴击、反击、状态、捕获、逃跑或魔法闪避.

### 8.3 战斗内装备变化

如果战斗技能导致装备被投掷、移除或销毁:

1. 先完成装备状态和库存差量.
2. 重算装备修正合计与有效运气.
3. 产生BaseLuck、EquipmentLuckModifier和EffectiveLuck对应的运行属性差量.
4. 后续事件使用新快照; 已经完成的判定不追溯重算.

单纯耐久降低但装备仍在槽内时不改变运气.

## 10. 一致性和失败处理

### 10.1 登录写回

运气刷新、刷新时间和最后登录时间属于一次账号档案写回. cache失败时:

- 恢复`base_luck`.
- 恢复`last_refresh_timestamp_ms`.
- 恢复`last_login_timestamp_ms`.
- 不设置character.online.
- 不发送成功响应.
- 不继续进入场景或战斗.

### 10.2 道具消费

使用运气戒指同时改变角色和库存. 推荐由Account actor串行完成:

1. 本地校验物品、数量、参数和角色状态.
2. 保存修改前角色与物品快照.
3. 在内存中设置基础运气并扣除道具.
4. 一次写回AccountRecord.
5. 失败时恢复两者并返回错误.
6. 成功后发送运气和库存差量.

### 10.3 并发

- 同一账号的角色登录、换装、道具和战斗创建由Account actor串行化.
- CombatRoom只读取开战快照, 不直接修改CharacterRecord.
- 战斗内装备变化产生的持久化请求必须回到Account actor; 失败必须阻止继续提交不一致的最终结算.
- 客户端提交的基础运气、装备修正或有效运气一律不可信.

## 11. 测试要求

### 11.1 LS时间

- `era`时刻映射到year=0、day=0.
- 5399秒仍为同一LS日, 5400秒进入下一LS日.
- 第99日到下一LS年的边界正确.
- 同LS日不同现实日期不刷新.
- 同现实日期跨90分钟LS边界, 下次登录刷新.
- 在线跨边界不刷新.

### 11.2 概率

对roll 0-99穷举:

- 运气1恰好40个值.
- 运气2恰好30个值.
- 运气3恰好20个值.
- 运气4恰好7个值.
- 运气5恰好3个值.

### 11.3 持久化

- 新角色保存待首次刷新状态.
- 首次登录刷新并持久化1-5.
- 同LS日重复登录不消耗随机数.
- 跨多个LS日只消耗一次随机数.
- cache失败完整恢复三个被修改字段, 角色保持离线.
- 非法luck_state在账号绑定校验时失败.

### 11.4 装备

- 无装备时有效运气等于基础运气.
- +1、+2、+5及超大正值均按1-5截断.
- 负修正最低截断为1.
- 两个装饰槽先相加再截断.
- 背包中的物品不参加.
- `ITEM_OTHER` luck列非0仍不参加.
- 耐久降低但未移除时修正不变.
- 装备移除或销毁后立即重算.

### 11.5 战斗

- 先制、物理闪避、暴击、玩家反击、普通异常、捕获、逃跑读取EffectiveLuck.
- 普通魔法闪避、职业魔法闪避和空手随机多段读取BaseLuck.
- 同一个角色装备+2时, 物理判定使用提高后的值, 魔法闪避仍使用原基础值.
- 合击跳过普通闪避, 不因目标有效运气产生Dodge随机抽取.
- 每次使用运气的CombatRandomCheck均携带正确luck_usage和快照.
